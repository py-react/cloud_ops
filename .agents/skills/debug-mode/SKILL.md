# Debug Logging Skill

This skill allows an agent to maintain a persistent, timestamped log of its activities. This is especially useful for debugging complex tasks, long-running processes, or when collaborating with other agents.

## Core Concepts

1. **Persistent `debug_id`**: For every task or logical session, you MUST generate a unique, descriptive `debug_id` (e.g., `feature-xyz-migration-2024-04-02`). Use this same ID for all logs related to that session.
2. **Real-time Logging**: Post log entries as you perform significant actions or encounter errors. This creates a durable record outside of the conversation history.

## Strict Constraints

To ensure high-fidelity debugging, you MUST follow these restrictions:
- **NO Snippet Isolation**: Do NOT use `run_command` to execute isolated code snippets for debugging. You must instrument the **actual project codebase** to observe its behavior in its true environment.
- **NO Bypass**: Do NOT use `run_command` or other tools to manually "push" logs that should be generated by the application runtime. All runtime data must come from the instrumentation added to the code.
- **User-Led Reproduction**: You are NOT allowed to "simulate" or "recreate" the bug yourself using terminal commands if the bug occurs in a complex environment (e.g., UI, multi-service). You MUST ask the **User** to recreate the bug after you have instrumented the code.


## API Payloads

The debug server expects the following JSON structures for efficient session management.

### 1. Hypothesis Set (Session Start)
When starting a session, the first piece of instrumented code should log the theories being tested.

```json
{
  "type": "hypothesis_set",
  "hypotheses": [
    {"id": 1, "desc": "Race condition in data fetching", "status": "PENDING"},
    {"id": 2, "desc": "Incorrect env variable configuration", "status": "PENDING"}
  ]
}
```

### 2. Runtime Log Entry
General diagnostic data captured during execution.

```json
{
  "timestamp": "YYYY-MM-DD HH:MM:SS",
  "message": "Step description",
  "data": { "key": "value" }
}
```

## Instrumenting Code with Telemetry

To understand how the code behaves at runtime, you should insert temporary logging statements directly into the source code. These statements should POST to the debug server.

### Python Example
```python
import requests
import json

def debug_log(id, message):
    try:
        requests.post(f"http://localhost:8000/debug/{id}", data=str(message))
    except Exception:
        pass

# DEBUG_START
debug_log("{debug_id}", f"Entering data_fetcher with params: {params}")
# DEBUG_END
```

### JavaScript / TypeScript Example
```javascript
async function debugLog(id, message) {
  try {
    await fetch(`http://localhost:8000/debug/${id}`, {
      method: 'POST',
      body: typeof message === 'object' ? JSON.stringify(message) : String(message)
    });
  } catch (e) {}
}

// DEBUG_START
debugLog('{debug_id}', `Value of state.user: ${JSON.stringify(state.user)}`);
// DEBUG_END
```

## Mandatory Debugging Protocol

When using this skill to troubleshoot, you MUST adhere to the following iterative process:

### 1. Analyze & Hypothesize
Analyze the codebase to identify relevant logic. Formulate a set of hypotheses for the bug. Do NOT use `curl` to post these yet.

### 2. Instrument & Verify
For each promising hypothesis:
1. **Instrument the Code**: Add the `debug_log` utility (see examples above) to the relevant source files.
2. **Post Hypotheses via Code**: Ensure the first line of execution in your instrumented code logs the `hypothesis_set` JSON structure.
3. **Anchor Markers**: Wrap all debug code in `# DEBUG_START` and `# DEBUG_END` comments.
4. **Internal Verification**: Confirm the telemetry endpoints are reachable.

### 3. Log Clearing & User Reproduction
**MANDATORY**: Before asking the user to verify a fix or recreate a bug, clear the previous logs using the `DELETE` API method to ensure a clean trace.

**User Action**: Ask the user to **recreate the bug** in their environment. This will trigger the runtime telemetry you added.

### 4. Failure Analysis via Runtime Logs
If the user reports an issue, check the debug server logs immediately using the `GET` API method. Use the runtime values and sequence of calls to refine your hypotheses.

### 5. Cleanup & Finalization
Once the user confirms the issue is **"fixed"**:
1. **Efficient Removal**: Delete all temporary telemetry code using the anchor comments.
   ```bash
   # Example: Remove lines between DEBUG_START and DEBUG_END
   sed -i '/DEBUG_START/,/DEBUG_END/d' path/to/file.py
   ```
2. Perform a final verification to ensure no regressions were introduced.
3. Finalize the session.


## Best Practices

- **Start every session** by logging the initial context and goals.
- **Log failure points** with as much detail as possible (errors, stack traces, terminal output).
- **Use meaningful `debug_id`s** that include the date and project name to avoid collisions.
- **Trust the Runtime**: If the logs from the debug server contradict your understanding of the code, prioritize the logs. The runtime telemetry is the ground truth.
